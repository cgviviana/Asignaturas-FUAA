📑 De los datos a las funcionalidadesDiapositivas explicativas

1. De la investigación al diseño de la solución

El desarrollo de una aplicación comienza antes de dibujar pantallas. En los encuentros anteriores se identificó un problema, se consultaron fuentes, se compararon soluciones existentes mediante benchmarking, se formuló una propuesta y se representaron procesos con diagramas de flujo. También se organizaron datos, cuando la propuesta lo requería, en tablas relacionadas.

1. Investigar¿Qué problema existe, a quién afecta y qué evidencias lo demuestran?
2. Comparar¿Qué hacen otras soluciones y qué necesidad permanece sin resolver?
3. Proponer¿Qué acciones debe permitir la solución? El diagrama describe cómo ocurre el proceso.
4. Organizar información¿Qué datos deben guardarse y cuáles necesitan vincularse?
5. Diseñar el productoEscribir requisitos en el PRD, escoger el MVP y diseñar la experiencia y las pantallas.

Ejemplo transversal: una institución necesita conocer las llegadas tardías. Primero se verifica el problema; luego se comparan mecanismos de registro, se representa el proceso de llegada y se identifican los datos que permitirán registrar y consultar cada caso. Este ejemplo ilustra el método, no define el proyecto de todos.

2. Cómo se conectan los datos de una aplicación

Una tabla reúne registros del mismo tipo. Cada fila representa un elemento (por ejemplo, una llegada) y cada columna describe una característica (fecha, hora o identificador). Una relación permite saber a qué estudiante y curso corresponde esa llegada, sin escribir repetidamente todos sus datos.

Tabla del ejemploDatos relevantesCómo se relaciona
EstudiantesID_Estudiante, nombre, ID_CursoCada estudiante está asociado a un curso mediante ID_Curso.
CursosID_Curso, nombre, hora de inicioUn curso agrupa varios estudiantes; define el horario que se compara con la llegada.
RegistrosID_Registro, ID_Estudiante, fecha, hora de llegada, estadoCada registro pertenece a un estudiante y un estudiante puede acumular varios registros.

Así se utiliza: cuando se registra la llegada de Camila, la aplicación localiza a qué curso pertenece, recupera su hora de inicio y la compara con la hora registrada. Sin el vínculo entre datos no podría hacer esa consulta de forma confiable.

En otros proyectos se utilizan otras entidades: un comercio podría relacionar clientes, pedidos y productos; una biblioteca, libros, usuarios y préstamos.

3. De una necesidad a una funcionalidad y su requisito

Se parte de una situación concreta y se describe qué podrá hacer la persona usuaria. Después se formula un requisito funcional específico y comprobable. El requisito se conecta con los datos que necesita y con una prueba que permita verificarlo.

Pregunta de diseñoEjemplo de aplicación
Necesidad: ¿qué problema debe resolverse?Consultar rápidamente las llegadas de un estudiante.
Funcionalidad: ¿qué acción debe permitir?Buscar un estudiante y consultar su historial.
Requisito funcional RF-02: ¿qué hará exactamente?Al seleccionar un estudiante, el sistema mostrará únicamente sus registros con fecha, hora y estado, ordenados del más reciente al más antiguo.
Datos: ¿de dónde sale la información?Estudiantes.ID_Estudiante vinculado con Registros.ID_Estudiante.
Comprobación: ¿cómo sabemos que funciona?Al consultar a Camila aparecen sus llegadas y no las de otros estudiantes.

Esta cadena es la que se documenta en el PRD. La pantalla será la forma visible de realizar la acción, pero su contenido viene de los datos previstos y del requisito.

4. Cómo un requisito se transforma en una pantalla de consulta

5. Verificar qué información requiere cada funcionalidad

Antes de diseñar una pantalla conviene comprobar qué información debe mostrar, capturar o calcular la función y si contamos con esos datos. Así se detectan campos ausentes y relaciones que todavía deben definirse.

FuncionalidadDatos que necesitaQué revisamos
Registrar una llegadaEstudiante, fecha y hora efectiva¿Se puede seleccionar un estudiante existente y guardar la llegada?
Calcular minutos tardeHora programada del curso y hora real de llegada¿El registro permite consultar el horario correspondiente?
Consultar historialIdentificador del estudiante, fechas y estados de sus registros¿La relación permite filtrar solo las llegadas de esa persona?

Ejemplo de una decisión: si se guardó la hora real pero nunca la hora programada, no se puede calcular correctamente el retraso. La revisión descubre esa necesidad antes de pedirle a Lovable que construya la función.

6. Escribir requisitos y criterios de aceptación

El documento de requisitos explica con precisión el comportamiento esperado. Una regla de negocio fija cómo se toma una decisión; un criterio de aceptación describe una situación que permite comprobar el resultado.

ElementoEjemplo aplicado
FuncionalidadRegistrar y consultar llegadas.
Requisito RF-01El usuario autorizado podrá seleccionar un estudiante, registrar fecha y hora de llegada y guardar el registro.
Regla de negocio RN-01Cuando la hora de llegada supere la hora programada del curso, el registro se clasificará como tardío según las reglas establecidas.
Criterio CA-01Al guardar la llegada de Camila a las 7:12 a. m. para una clase de las 7:00 a. m., el sistema crea un registro con 12 minutos de retraso.
Criterio CA-02El nuevo registro aparece en el historial de Camila, sin modificar los de otros estudiantes.

Conexión con la siguiente sección: estas decisiones se reúnen en el PRD. Después, el MVP indica cuáles serán indispensables para la primera versión.

📑 Documento PRD y producto mínimo viableDiapositivas explicativas

1. ¿Qué es y para qué se hace un PRD?

El Documento de Requisitos del Producto (PRD) explica qué problema resolverá la aplicación, para quién, qué debe hacer y cómo sabremos que funciona. Sirve para orientar tanto el diseño como la construcción con herramientas de IA.

Necesidad¿Cuál es el problema observado y con qué evidencia se sustenta?
Usuarios¿Quiénes usan la app y qué deben poder hacer?
Funcionalidades¿Qué tareas debe permitir completar?
Criterios de aceptación¿Cómo se verifica que cada tarea funciona?

2. Así se transforma una necesidad en PRD

ApartadoEjemplo ilustrativo
ProblemaLas llegadas se anotan manualmente y cuesta consultar su historial
UsuarioDocente que registra y consulta llegadas
FuncionalidadRegistrar estudiante, fecha y hora de llegada
DatosEstudiante, curso, fecha y hora
Criterio de aceptaciónAl guardar, aparece un registro asociado con el estudiante correcto

El PRD no es una lista de pantallas bonitas: conecta necesidades con comportamientos verificables.

3. ¿Qué significa MVP?

El Producto Mínimo Viable (MVP) es la primera versión que reúne las funciones indispensables para comprobar que la solución aporta valor. Se define a partir del PRD, priorizando lo esencial.

ProblemaNo existe una consulta rápida de llegadas.
MVPRegistrar una llegada y consultar el historial.
Versión posteriorAlertas, reportes avanzados o predicciones, si hacen falta.
Comprobación¿El usuario logra registrar y consultar sin ayuda?

4. Qué entra en la primera versión: decisión del MVP

Funcionalidad propuesta¿En primera versión?Por qué
Registrar llegadasSíResuelve la necesidad central
Consultar historialSíPermite comprobar lo guardado
Personalizar diez temas de colorNo prioritarioNo resuelve la necesidad principal
Predicción avanzada de ausenciasEvaluar despuésExige más datos y validación

En cualquier proyecto: se priorizan las funciones que permiten probar la idea con el menor alcance razonable.

5. Plantilla completa del PRD: qué contiene cada apartado

Un PRD es el acuerdo sobre qué se va a desarrollar, para quién y cómo se verificará. Se prepara antes de pedirle a la IA que genere pantallas.

Apartado de la plantillaQué se escribeEjemplo breve
Nombre y versiónTítulo, fecha, responsable y versiónControl de llegadas, versión 0.1

Usuarios y rolesQuién usa la app y qué puede hacerDocente registra; coordinación consulta
Objetivo y alcanceResultado esperado y límitesRegistrar y consultar llegadas de prueba
FuncionalidadesAcciones concretas del usuarioCrear registro, buscar historial

6. Plantilla PRD: un requisito completamente diligenciado

Código: RF-02 Nombre: Consultar historial

Usuario: personal autorizado

Descripción: al seleccionar una persona, la aplicación presenta únicamente los registros asociados con ella, con fecha, hora y estado.

Entrada: identificador de la persona seleccionada.

Proceso: buscar los registros vinculados mediante la relación entre tablas y ordenarlos por fecha.

Salida: lista de llegadas con fecha, hora y estado.

Criterio de aceptación: si se selecciona a Camila, aparecen únicamente sus registros; si no tiene, se informa «Sin registros».

Esta estructura sirve para reservas, inventarios o solicitudes: cambia el objeto consultado, no el modo de documentar.

7. Plantilla del MVP: decidir qué se construye primero

El MVP es una primera versión que permite probar la utilidad de la solución con un alcance controlado; no significa una app descuidada ni insegura.

Ficha MVPEjemplo diligenciado
Hipótesis de valorRegistrar y consultar llegadas reducirá el tiempo de búsqueda
Usuario principalDocente que registra llegadas
Funciones imprescindiblesSeleccionar estudiante, registrar hora, consultar historial
Datos mínimosIdentificador, fecha, hora y estado
Fuera del MVPAlertas avanzadas e informes predictivos
Prueba de validaciónRegistrar tres llegadas ficticias y comprobar que se consultan
IndicadorTiempo necesario para localizar un registro
LímiteSolo datos simulados durante la demostración

Relación: el PRD describe el producto previsto; el MVP selecciona qué parte se comprobará primero.

8. Del documento al generador de aplicaciones

La herramienta de IA necesita instrucciones que pueda implementar. No es suficiente escribir «haz una app bonita».

Requisito RF-02→Tablas vinculadas→Pantalla historial→Prueba con datos ficticios

Fragmento útil para Lovable: «Crea una pantalla de historial. Al elegir una persona, consulta únicamente los registros vinculados con su identificador. Muestra fecha, hora y estado. Si no hay registros, presenta un mensaje vacío. Usa datos de demostración».

Comprobación: si se muestra un historial sin diferenciar personas, se incumple el requisito aunque la pantalla sea atractiva.

📑 Experiencia de usuario, UX y maquetaciónDiapositivas explicativas

1. De la tarea del usuario al diseño de la experiencia

El diseño UX comienza preguntando quién usa la aplicación, qué necesita lograr y en qué condiciones la utilizará. A partir de una funcionalidad del PRD se construye un recorrido para completar esa tarea.

UsuarioEjemplo: un docente autorizado que registra la llegada de un estudiante.
ObjetivoGuardar una llegada correctamente y confirmar que quedó registrada.
SituaciónLa clase está comenzando; necesita pocos pasos, letras legibles y campos claros.
RecorridoInicio → Registrar llegada → Seleccionar estudiante → Completar hora → Guardar → Confirmación.
Error posibleSi falta el estudiante, mostrar qué debe corregirse sin borrar la información ingresada.

El ejemplo muestra cómo se piensa una experiencia. Cada proyecto debe analizar su propio usuario y tarea principal.

2. Cuatro decisiones que construyen una buena pantalla

Estos conceptos trabajan sobre la misma tarea, pero responden preguntas diferentes. Se aplican en orden, no son nombres alternativos para un dibujo.

EtapaPregunta que resuelveDecisión aplicada a «Registrar llegada»
UX: experiencia¿La persona puede completar la tarea fácilmente?Seleccionar estudiante, ingresar hora, guardar y recibir confirmación.
Arquitectura¿Qué pantallas existen y cómo se pasa de una a otra?Inicio → Registrar llegada → Confirmación → Historial.
Wireframe¿Dónde va cada elemento y en qué orden?Título; selector de estudiante; fecha; hora; botón principal; mensaje.
UI y mockup¿Cómo se verá y se leerá cada elemento?Etiquetas visibles, contraste, tamaño táctil, color del botón y mensajes claros.

Prototipo: versión que permite recorrer y probar la interacción propuesta. Puede ser visual, simulada o conectada a datos según el alcance.

3. Primero se define el recorrido entre pantallas

Una pantalla aislada no explica la experiencia completa. El recorrido debe mostrar qué hace el usuario, qué responde la aplicación y cuál es el siguiente paso.

Inicio
Elegir «Registrar»→Formulario
Completar datos→Validación
Verificar campos→Confirmación
Registro guardado→Historial
Consultar resultado

Ruta alternativa: si falta la hora, no se guarda; aparece «Ingresa la hora de llegada», el campo queda señalado y la persona puede corregirlo.

Regla para otras aplicaciones: cada tarea principal necesita una entrada, una acción, una respuesta del sistema y, cuando corresponda, una ruta de error.

9. La arquitectura de información define el mapa de pantallas

El mapa de navegación explica qué pantallas existen y desde dónde se llega a cada una. No es lo mismo que el diagrama de flujo del algoritmo.

Inicio
Registrar llegada Formulario
Historial Lista de registros
Detalle Información de un registro

Decisión de diseño: desde Inicio se accede a Registrar e Historial; al seleccionar un elemento del Historial se abre Detalle. El nombre de cada pantalla debe describir su propósito.

En una app de reservas podrían ser «Buscar», «Reservar», «Mis citas» y «Detalle». El método es el mismo, no las pantallas obligatorias.

11. Cómo se revisa un diseño UX antes de construirlo

Imagina que otra persona observa la maqueta por primera vez. Debe poder explicar dónde inicia, qué completa y cómo reconoce el resultado.

Pregunta de revisiónSeñal de un diseño claro
¿La tarea principal es visible?El botón o acceso se identifica sin buscar entre muchas opciones
¿Los campos se entienden?Etiquetas específicas y controles apropiados al dato
¿Qué pasa si se equivoca?Mensaje de error comprensible y opción de corregir
¿Se confirma el resultado?La interfaz comunica si se guardó o no

12. De la maqueta a la construcción asistida por IA

La herramienta de desarrollo necesita instrucciones más precisas que «haz una app bonita». La maqueta sirve como referencia de estructura y la ficha explica el comportamiento esperado.

Fragmento de especificación para Lovable:

«Crea una pantalla llamada “Registrar llegada”. Usa un encabezado, un selector de persona, campos de fecha y hora y un botón “Guardar llegada”. El selector consulta las personas existentes; al guardar se crea un registro asociado con la persona elegida. Si falta un campo obligatorio, muestra un mensaje específico. Si el registro se guarda, muestra confirmación y un enlace al historial. Diseña para pantalla móvil, con etiquetas visibles y buen contraste».

Qué se aporta a la IA: requisito verificable + origen de datos + componentes + reglas + navegación + estilo y accesibilidad. Después se comprueba el resultado; describirlo no garantiza su implementación.

No-code: construir funcionalidades mediante interfaces visuales y configuraciones, sin escribir manualmente la mayor parte del código. Desarrollo asistido por IA: describir el producto en lenguaje natural para que una herramienta proponga o genere componentes, que luego se revisan y prueban.

No-codeSe configuran datos, reglas y pantallas desde un editor visual.

📑 Construcción en Lovable y prompt de desarrolloDiapositivas explicativas

1. Los insumos que recibe la herramienta

El punto de partida no es pedir «hazme una aplicación». Se utiliza la información preparada: problema, usuarios, PRD, alcance MVP, tablas y relaciones, y maquetas.

PRD→MVP→Datos y relaciones→UX / maquetas→Prompt

Un buen prompt transforma estas decisiones en instrucciones para crear y probar el prototipo.

2. Seis partes de un prompt de desarrollo

1. Contexto y usuariosQué problema se resuelve y quién utilizará la aplicación.
2. Alcance MVPQué debe funcionar en la primera versión.
3. Datos y relacionesTablas, campos, identificadores y vínculos.
4. Funciones y reglasAcciones disponibles y condiciones para realizarlas.
5. Pantallas y UXPantallas, navegación y organización visual.
6. ComprobacionesQué se considera un resultado correcto y qué debe probarse.

3. Ejemplo aplicado: prompt de retardos

Crea un prototipo para registrar y consultar llegadas académicas. Usuarios: docente que registra y consulta. MVP: registrar una llegada y consultar el historial. Datos: Estudiantes (ID, nombre, curso); Cursos (ID, nombre, hora de inicio); Registros (ID, estudiante, fecha, hora de llegada, estado). Relaciones: cada Registro pertenece a un Estudiante; un Estudiante pertenece a un Curso. Pantallas: Inicio, Registrar llegada, Historial y Detalle. UX: formulario claro para celular, confirmación tras guardar y navegación visible. Comprobación: al guardar una llegada, aparece correctamente asociada en el historial. Antes de afirmar que hay persistencia real, verifica que exista una base de datos conectada y operativa.

El ejemplo ilustra la estructura. Cada equipo reemplaza entidades, datos y reglas según su solución.

4. Cómo revisar el resultado generado

Crear proyecto→Describir requisitos→Revisar vista previa→Probar flujos→Ajustar prompt

La vista previa puede mostrar pantallas sin que exista todavía almacenamiento real. Debe comprobarse por separado si la información se guarda, se consulta y está protegida.

Pantallas¿Aparecen las que requiere el MVP?
Datos¿Los registros se guardan y se relacionan correctamente?
UX¿Se puede completar el recorrido desde celular?
Correcciones¿La nueva instrucción describe exactamente qué cambiar?

5. Cómo redactar un prompt que produzca una aplicación verificable

Parte del promptQué debe especificarse
ContextoProblema real y objetivo del producto
Usuarios / rolesQuién registra, consulta o administra
Datos / relacionesTablas, campos, identificadores y vínculos
Funciones y reglasAcciones, validaciones, cálculos y condiciones
UX y pantallasSecciones, navegación, wireframes y mensajes
Pruebas / límitesCriterios de aceptación, datos ficticios y asuntos pendientes

Si la herramienta no puede deducir una regla, debe solicitar precisión en lugar de inventarla; por ejemplo, cuándo se considera tardía una llegada.

6. Ejemplo de mejora iterativa en Lovable

Versión inicial del pedido: «Crea una pantalla para registrar llegadas».

Revisión: el formulario no permite identificar al estudiante ni confirma que se guardó.

Prompt de mejora: «En la pantalla Registrar, añade un selector vinculado con la tabla de personas, un campo de hora obligatorio y el botón Guardar. Al guardar, crea un registro asociado con la persona seleccionada y confirma el resultado. Si falta un dato, muestra el mensaje junto al campo y conserva la información escrita».

Prueba: guardar con datos completos y sin seleccionar persona; comprobar que los resultados sean diferentes.

📑 Funciones de inteligencia artificialDiapositivas explicativas

1. IA dentro de una app: ¿cuándo aporta valor?

Una función de IA puede ayudar a clasificar, resumir, recomendar o interpretar información cuando esa capacidad atiende una necesidad real. No se incorpora solo por adornar el producto.

ClasificaciónIdentificar una categoría a partir de texto o una imagen.
Asistente conversacionalResponder preguntas sobre información pertinente.
ResumenSintetizar observaciones o reportes.
RecomendaciónSugerir una acción según datos disponibles.

2. Ejemplo: función de IA conectada al propósito

NecesidadFunción posiblePrecaución
Muchos reportes de observacionesResumir patrones frecuentesRevisar la precisión del resumen
Consultas repetidas de usuariosAsistente de preguntas frecuentesLimitarlo a fuentes válidas

La aplicación de retardos podría resumir tendencias, pero eso es una ampliación posible, no un requisito universal.

3. Herramientas e integración

Teachable MachineEntrenar clasificadores sencillos de imágenes, sonidos o poses; el uso en una app requiere integrar el modelo.
LovableDesarrollar la interfaz y conectar servicios o funciones cuando el proyecto y la plataforma lo permitan.
Servicio de IA mediante APIProcesar texto o imágenes; implica conexión técnica, costos, privacidad y protección de credenciales.
Flujos de automatizaciónConectar eventos y servicios; hay que comprobar permisos, límites y condiciones del plan.

4. Diseñar una función de IA con propósito

Una función de IA debe resolver una tarea concreta que no resulte mejor con una regla simple.

Necesidad¿Hace falta IA?Motivo
Calcular minutos entre dos horasGeneralmente noEs un cálculo determinista
Buscar un registro por fechaGeneralmente noSe resuelve con filtros
Resumir muchos comentarios abiertosPuede aportarInterpreta lenguaje natural, requiere revisión
Responder consultas sobre una base documentalPuede aportarNecesita fuentes, permisos y control de respuestas

Para cada función hay que definir datos de entrada, resultado esperado, límites, revisión humana y tratamiento de información personal.

📑 Pruebas y mejora del prototipoDiapositivas explicativas

1. ¿Qué significa probar un prototipo?

Probar es comprobar, mediante casos concretos, si la aplicación cumple los requisitos y si las personas pueden completar las tareas previstas. No basta con mirar las pantallas.

Requisito→Caso de prueba→Resultado esperado→Resultado observado→Corrección

Ejemplo: al guardar una llegada, debe aparecer en el historial del estudiante seleccionado.

2. Casos de prueba de ejemplo

CasoAcciónResultado esperado
RegistrarSeleccionar persona, indicar hora y guardarAparece un nuevo registro
ConsultarAbrir historial de la personaSe ven sus registros, no los de otra
Dato incompletoIntentar guardar sin un campo obligatorioSe muestra un aviso claro
MóvilCompletar el flujo en pantalla pequeñaSe puede leer y pulsar sin desplazamientos confusos

Las pruebas deben adaptarse a las funciones de cada proyecto.

3. Cómo mejorar con instrucciones precisas

Problema observado«Al guardar, el formulario se cierra, pero el registro no aparece en historial».
Cambio pedido«Revisa el guardado y enlaza el historial con los datos persistidos; muestra confirmación solo después del éxito».
VerificaciónRepetir la prueba con un registro nuevo y comprobar el resultado.
EvidenciaRegistrar qué funcionó, qué falló y qué se ajustó.

📑 Sustentabilidad, aspectos legales y presentaciónDiapositivas explicativas

1. Del prototipo al uso sostenido

Para que una solución pueda funcionar más allá de una demostración hay que considerar personas, mantenimiento, recursos y condiciones reales de uso.

Sostenibilidad técnicaActualizaciones, soporte, copias de seguridad y disponibilidad.
Sostenibilidad económicaCostos de plataforma, base de datos, almacenamiento y uso de IA.
CapacidadNúmero de usuarios, límites y comportamiento cuando crece la demanda.
AccesibilidadUso comprensible desde distintos dispositivos y necesidades.

2. Aspectos jurídicos y uso responsable

Protección de datosDefinir qué información se recopila, para qué, quién puede verla y cómo se protege.
Derechos de autorRevisar permisos de textos, imágenes, marcas, diseños y materiales incorporados.
Términos de herramientasVerificar licencias, condiciones comerciales y uso de contenido generado con IA.
Responsabilidad por el productoLa intervención de IA no elimina la necesidad de revisar originalidad, seguridad y funcionamiento.

El uso de IA no implica automáticamente que el diseño sea ilegal o demande a su creador. El riesgo depende del contenido utilizado, los derechos involucrados, el uso y la jurisdicción; se requiere revisión del caso concreto.

3. Antes de compartir con usuarios reales

Pregunta de revisiónQué debe verificarse
¿Dónde quedan los datos?Almacenamiento, permisos, respaldos y eliminación
¿Qué pasa si aumentan los usuarios?Planes, límites, costos y rendimiento
¿Quién mantiene la aplicación?Responsable de corregir fallos y actualizar
¿Podemos usar todos los recursos?Licencias, atribuciones y políticas de privacidad

Un enlace público no equivale a tener un producto listo para operar.

4. Presentar la propuesta de valor

Problema→Usuarios→Solución→Demostración→Valor

La presentación debe mostrar el problema que se investigó, explicar la funcionalidad prioritaria del MVP y demostrar un recorrido real del prototipo. También debe reconocer lo que aún está en desarrollo.

Propuesta de valor¿Qué mejora frente a la situación actual o a otras alternativas?
Evidencia¿Qué prueba o demostración respalda que funciona?

5. Ficha de viabilidad para pasar a uso real

AspectoPregunta de verificación
Usuarios¿Cuántos usarán la app simultáneamente?
Costos¿Qué se cobra por usuarios, uso, almacenamiento o funciones de IA?
Datos¿Dónde se guardan, quién los consulta y cómo se respaldan?
Seguridad¿Cómo se autentican los usuarios y se controlan sus permisos?
Privacidad¿Existe fundamento para recoger datos personales, información y avisos adecuados?
Propiedad intelectual¿Se tienen derechos o licencias para imágenes, textos, código y datos utilizados?
IA¿Se informan sus límites y se revisan sus resultados?
Continuidad¿Quién mantiene la app y atiende fallos?

En Colombia, el tratamiento de datos personales requiere considerar la Ley 1581 de 2012 y las obligaciones aplicables. La viabilidad jurídica depende del caso: crear algo con IA no implica por sí solo que sea ilegal o automáticamente demandable.
